# Data / Config Model

Purpose: Defines the structured artifacts ARDS reads and writes. ARDS has no database — this document is the closest equivalent: the shape of the data every skill passes to every other skill.
Last Updated: 2026-07-08
Related Documents: 01_PRD.md, 02_INFORMATION_ARCHITECTURE.md, DECISION_LOG.md
Version: 0.5

## Why this doc exists despite there being no database

The original template this doc set is adapted from assumed a Supabase-backed application with persisted entities. ARDS persists nothing server-side — every artifact below is a file (JSON/markdown/HTML) produced in a session and handed to the user or the next skill. This document plays the same *role* a schema would: it's the single place that defines each artifact's shape so skills stay compatible with each other.

## Artifacts (the "entities")

### 1. Client configuration block
Generated by `system-setup` Step 3, the master reference for a single client engagement. Read by every other skill.

```json
{
  "project": "~~project name",
  "brand_tier": {
    "icon_library": "heroicons", "icon_library_override": null,
    "font_system": "google-fonts", "font_system_override": null,
    "asset_library": "unsplash", "asset_library_override": null
  },
  "product_tier": {
    "base_design_system": "radix-shadcn",
    "token_format": "dtcg-json",
    "platforms": ["web", "mobile"],
    "data_viz_library": "recharts", "data_viz_override": null
  },
  "brand_strategy": { "status": "not_started", "source_file": null, "refero_style_profile": null },
  "copy_mechanics": { "voice": null, "tone_rules": null, "reading_level": null }
}
```
(Source: README.md and `system-setup/SKILL.md` Step 3 — these two copies are currently identical; if they ever drift, `system-setup/SKILL.md` is authoritative since it's the skill that generates the block.)

### 2. Design token file
Generated by `system-setup` Step 4, mutated by `token-update`. W3C DTCG format, split by platform (`tokens.web.json`, `tokens.mobile.json`). Three-tier alias chain, enforced as a hard rule in both skills:

```
primitive  → can contain raw values (hex, px, string)
  ↑ alias
semantic   → must alias to a primitive, e.g. {color.palette.brand.500}
  ↑ alias
component  → must alias to a semantic token, e.g. {color.brand.primary}
```

A component token must never alias directly to a primitive — no level-skipping. Categories: `color`, `typography`, `spacing`, `radius`, `elevation`, `motion`, `shadow`. Two modes: `light`, `dark`. Full schema: `skills/system-setup/references/token-architecture.md`. Full alias rules: `skills/token-update/references/alias-rules.md`.

`token-update` adds a `_meta` block on every write:
```json
{ "_meta": { "version": "x.x.x", "updated": "YYYY-MM-DD", "change": "..." } }
```
Patch/minor/major increments follow semver rules stated in `token-update/SKILL.md` Step 4.

### 3. Figma variable spec
Output of `system-setup` Step 5. Either a live write (via `mcp__Figma__get_variable_defs` when the Figma MCP is connected) or a structured text definition (name, value per mode, scope, group) when it isn't. Not a persisted ARDS artifact — it's a transformation of the token file into Figma's variable model.

### 4. Claude Design JSON
Output of `asset-generation` Step 6 — a structured design spec (`claude_design_version`, `meta`, `tokens`, `layers[]`) that the Figma MCP can implement directly. Every fill/stroke/radius/padding/gap must carry a `"token"` reference back to the token file (artifact #2); this is the enforcement point that keeps generated screens from drifting off-token. Full shape: `asset-generation/SKILL.md` Step 6.

### 5. Audit report
Output of `system-audit`. Not persisted as a file format of its own — a structured findings block (`LAYER` / `STATUS` / `Findings` with severity) plus a summary table. Reads artifacts #1 and #2 as its reference; reads a Figma URL, screenshot, upload, or copy block as its subject.

### 6. Copy block
Output of `copy-generation`. Reads `copy_mechanics` from artifact #1. Emits 2–3 labeled variants (A/B/C) per request, always preceded by a Voice/Tone/Mechanics declaration. See `skills/copy-generation/references/copy-mechanics.md` for the full mechanics catalog.

## Relationships

```
Client Config (1) ──generates──► Token File (2) ──transforms-to──► Figma Variable Spec (3)
      │                                │
      │                                └──referenced-by──► Claude Design JSON (4), Audit Report (5)
      └──referenced-by──► Copy Block (6), Audit Report (5)
```

- `system-setup` produces (1) and (2), transforms (2) into (3).
- `token-update` mutates (2) only — it never touches (1).
- `asset-generation` reads (1) and (2) to produce (4).
- `copy-generation` reads (1) to produce (6).
- `system-audit` reads (1), (2), and whatever's being audited (a Figma file, upload, or copy block) to produce (5).

## Status

This is the current, real shape of every artifact ARDS produces, sourced directly from the SKILL.md files that generate them (verified 2026-07-08) — not a forward-looking schema. If a skill's output shape changes, this doc and the skill's own version history table should be updated together.
